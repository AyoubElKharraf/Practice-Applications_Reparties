# 🌐 VERSION 1 : Communication à distance (Messages & Commandes)

### 1. Objectif technique
Cette version établit un canal de communication TCP pur entre deux machines distantes connectées au même réseau (LAN ou Wi-Fi).
- **Le Serveur** écoute sur toutes les interfaces réseau (`INADDR_ANY`), inspecte la machine avec `getifaddrs()` et affiche ses adresses IP physiques pour vous indiquer immédiatement quelle commande taper sur le client.
- **La Concurrence** : Le serveur utilise `fork()` pour traiter plusieurs machines clientes distantes simultanément sans blocage.
- **Le Client** résout l'adresse IP (`gethostbyname`), s'y connecte et fournit un shell `distant> ` pour envoyer des messages ou interroger le serveur.

---

Dans le terminal (sur les deux machines ou la machine de test) :
```bash

# 📦 VERSION 2 : Transfert Multi-Données à distance (Fichiers, Vidéos, Binaires)

### 1. Pourquoi transférer des données est différent d'un simple message ?
- **Nature du flux TCP (Byte Stream)** : TCP ne préserve pas les limites des messages. Si vous envoyez une image de 5 Mo d'un coup, `send()` peut n'en envoyer qu'une partie, ou le récepteur peut recevoir des fragments éparpillés.
- **Solution implémentée** : 
  1. **En-tête de protocole** : le client ou serveur annonce d'abord le nom du fichier et sa taille exacte en octets : `PUT_REQUEST <nom> <taille>\n` ou `GET_REQUEST <nom>\n`.
  2. **Streaming par blocs (`CHUNK = 4096 octets`)** via [ftp_common.h](file:///c:/Users/DELL/Documents/Master/Master_M2I/SEMESTRE%203/Applications%20R%C3%A9parties/TPs/TP%201%20-%20Socket%20C/tp1_socket_c/ex2/ftp_common.h).
  3. **Suivi visuel en temps réel** : une barre de progression interactive s'affiche en direct pendant le transfert des gros fichiers.
  4. **Sécurité Chroot / Sandbox** : un client distant ne peut pas inspecter tout le disque dur de la Machine 1 ; il est confiné dans un dossier racine (`~/racine_ftp`) et les chemins tentant une évasion (ex: `../../etc/passwd`) sont systématiquement rejetés.

> **Résultat :** Téléverse la donnée binaire de la Machine 2 vers la Machine 1. Vous voyez la barre de progression défiler :

```
> **Résultat :** Télécharge la vidéo de 3 Mo de la Machine 1 vers la Machine 2 :
> ```text
>   Téléchargement [==============================] 100% (2.86 / 2.86 Mo)
>   [Succès] Fichier 'video.bin' reçu et enregistré avec succès !
> ```

```text

transfert> pwd
transfert> cd ..
transfert> cd ..
```
> **Résultat :** Le deuxième `cd ..` est immédiatement **refusé** par la sécurité du serveur (`Accès refusé : tentative de sortie de la racine`), garantissant que la machine cliente ne peut pas pirater les fichiers hors du dossier partagé.

```text
transfert> quit
```

#### 🔹 Étape 7 : Preuve mathématique d'intégrité (Vérification Checksum SHA-256)
Pour prouver au professeur ou lors de votre évaluation que le fichier binaire transféré n'a subi **aucune corruption ni perte d'octet** :
- Sur la **Machine 1** :
  ```bash
  sha256sum ~/racine_ftp/video.bin
  ```
- Sur la **Machine 2** :
  ```bash
  sha256sum video.bin
  ```
Les deux empreintes hexadécimales de 64 caractères sont **strictement identiques**.
